**Agent 技术进展与个人探索路线：记忆、上下文工程、Harness**

调研截止：2026 年 10 月 7 日。面向有后端开发经验、希望利用业余时间理解并实验 Agent 系统的程序员。

本报告优先采用论文、作者发布的实现、官方工程文章和当前文档。2025 年材料作为技术起点，2026 年资料用于观察具体进展。下文区分三种证据：论文的特定实验结果、厂商工程案例、本文建议的个人实验。调研没有运行这些系统，也没有复现论文成绩；“值得学习”的排序是结合你的目标作出的判断，不是全领域的技术排名。

**我的建议是把“可靠地完成多步任务”作为学习主线。** 先理解执行循环、状态、上下文选择和验证，再学习长期记忆与经验优化。你可以同时保留一个好玩的环境，例如三个城邦的外交与贸易，但让每次技术改动回答一个可比较的问题。

| 技术方向 | 近期值得关注的变化 | 对你的学习价值 | 建议次序 |
| --- | --- | --- | --- |
| Harness / 运行系统 | 从提示词加循环，发展到状态持久化、环境管理、恢复、验证和预算控制 | 与事务、重试、状态机等后端知识直接相连 | 最先学 |
| 上下文工程 | 按需加载、工具结果外置、压缩、结构化交接、类型化保留 | 解释为什么信息都在，Agent 仍可能做错 | 最先学 |
| 长期记忆 | 从存历史和向量检索，扩展到更新、失效、经验、来源和隔离 | 很适合做低成本、可观察的实验 | 第二阶段 |
| 评估 | 从答案评分转向终态、轨迹、重复可靠性和完整成本 | 是判断其他技术是否有效的基础 | 从第一天开始 |
| 经验与提示优化 | 用失败轨迹改进上下文、程序性知识和提示 | 可以不训练模型权重就开展探索 | 有基线后再学 |
| RLM / 程序化上下文 | 把大输入留在外部环境，由代码和子调用处理 | 适合日志、历史事件、资料分析 | 进阶探索 |
| 多 Agent | 通过任务与上下文隔离获得收益，也引入协调成本 | 值得理解，但应与单 Agent 和固定工作流比较 | 后置 |
| Agentic RL | 训练工具使用、压缩后推理、任务分解等行为 | 有研究价值，复现成本和评估难度较高 | 先读论文 |

**先把这些概念放在同一个系统里理解。** 下表是一组工程划分，不是所有厂商共同遵守的标准分类。

| 概念 | 它主要回答的问题 | 城邦实验中的对应物 |
| --- | --- | --- |
| 模型 | 在收到的信息与动作空间下，预测或选择什么？ | 提议交易、接受结盟 |
| Harness | 如何组织模型、工具、状态、执行反馈和结束条件？ | 决策循环、校验、执行、失败恢复 |
| 执行环境 / Sandbox | 任务在哪里运行，能够访问和修改什么？ | 模拟器、文件或隔离容器 |
| 上下文工程 | 这一轮让模型看到哪些信息，以什么形式看到？ | 当前观察、相关事件、约束、工具说明 |
| 记忆 | 跨回合、跨任务保留什么，什么时候更新或取出？ | 违约事件、经验、关系判断 |
| 持久业务状态 | 系统认可的事实是什么？ | 粮食余额、已成交交易、正式盟约 |
| 评估 | 怎样知道任务完成，规则满足，成本合理？ | 终态断言、失败分类、重复运行比较 |

OpenAI 当前架构文档明确分开 harness、执行环境和应用服务器；harness 可以调用远程工具而不拥有计算环境。这个划分有助于避免把 SDK、容器和 Agent 本身当作同一层。[OpenAI：Architecture](https://developers.openai.com/api/docs/guides/agents-api/architecture)

在个人实验中，建议始终保留四类信息的边界：世界实际发生的事实、某个 Agent 能看到的观察、它形成的推断、它准备执行的动作。例如“B 没有按约交货”是事件，“B 一定不可信”是解释，“停止与 B 贸易”是行动。一个记忆系统不应把它们无条件合并成一条永远有效的事实。

**上下文工程的进展，主要体现在信息如何进入、离开和留在模型的工作集。**

2025 年的 Anthropic 工程文章把上下文管理扩展到系统指令、工具、外部数据和历史，并讨论按需检索、压缩、外部笔记与上下文隔离。它的价值是给出可操作的设计思路，而非证明某一种组合在所有模型上最好。[Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

Chroma 的 2025 年研究在 18 个当时的模型上观察到长输入下的不均匀性能，并用干扰信息、语义匹配等任务扩展简单的“大海捞针”评测。这支持你实际测试信息位置和噪声的影响；它没有证明所有 2026 年模型具有相同下降幅度，也没有解释完整的内部机制。[Context Rot](https://www.trychroma.com/research/context-rot)

值得掌握的操作有五个：写入外部状态；选择本轮相关信息；压缩可损失的历史；隔离不同任务的上下文；在执行前重新获取时效敏感的事实。它们共同影响效果，不能只通过上下文 token 数判断质量。

**进展一：工具与知识逐步按需加载。** Anthropic 在 2025 年 11 月发布 Tool Search 与 Programmatic Tool Calling；OpenAI 当前文档也提供延迟加载的工具搜索。它们减少无关工具定义和中间结果进入上下文的机会。工具少且说明短时，搜索步骤可能只增加延迟，个人项目不必一开始实现工具市场。[Anthropic：Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)、[OpenAI：Tool search](https://developers.openai.com/api/docs/guides/tools-tool-search)

Skills 的公开格式采用逐步加载：先看名称和描述，需要时读完整指令，再加载资源或脚本。它适合存放程序性知识，例如“如何检查一笔交易”，不应把可变余额藏在技能文件里。[Agent Skills 标准说明](https://agentskills.io/home)

**进展二：更多中间处理留在代码执行环境。** OpenAI 当前 Programmatic Tool Calling 允许模型生成 JavaScript 来组合工具、过滤或聚合结果。它的托管 V8 运行时与通用 Node.js 或持久文件工作区不同。学习时要看清执行能力和生命周期；代码编排也不能替代写操作的授权、参数校验和幂等设计。[OpenAI：Programmatic Tool Calling](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling)

可做的实验是让 Agent 分析交易日志：一组逐条把工具结果交给模型，另一组由代码计算总额与异常候选，再把必要证据交给模型。比较总调用数、输入输出 token、漏报、误报，以及最终结论能否回指原始记录。返回得更少可能更便宜，也可能隐藏了需要推理的证据。

**进展三：压缩成为运行系统能力，但仍需要独立验证。** OpenAI 当前支持阈值触发的服务端 compaction 与独立 compact 调用；返回的压缩项是不可直接阅读的状态，用于后续推理续接。它与自己维护的可读交接记录用途不同，不能用来替代业务数据库或审计日志。[OpenAI：Compaction](https://developers.openai.com/api/docs/guides/compaction)

这里有一个容易混淆的点：prompt/KV cache 主要减少重复计算或影响推理资源；上下文压缩减少活动输入；外部长期记忆保存供以后取用的信息；训练中的参数变化改变模型本身。它们的作用域、更新方法和失效方式不同。

**进展四：开始按信息类型决定保真度。** 2026 年 8 月的《The Compaction Cliff》研究提出 Knowledge Triage，让约束、程序、信念、偏好和历史采用不同的保留策略。最值得借鉴的是“有些内容必须精确保留，有些可以摘要”的思想。其实验样本与分类器有局限；存储层保留规则，不代表模型执行时一定遵守规则。[论文与局限](https://arxiv.org/html/2608.22752v1)

你的版本可以不训练分类器：先人工标注小样本，把动作权限、金额、未决操作 ID 等放进受保护字段，把一般历史放进摘要。检查压缩后是否仍能识别“请求已提交但结果未知”，而不是误写成“请求失败，可以重试”。重要限制还应在动作执行端校验。

**进展五：上下文管理本身成为模型要学习的动作。** AgentFold 让模型选择不同尺度的历史折叠，通过监督微调学习何时整理工作区；ReSum 研究周期摘要，并用 ReSum-GRPO 训练对压缩状态的推理。论文中的成绩来自具体搜索任务和训练设置。用提示词模仿 folding 只能算机制探索，不能称为复现训练结果。[AgentFold，2025-10](https://arxiv.org/abs/2510.24699)、[ReSum，2026-03 修订](https://arxiv.org/abs/2509.13313)

**长期记忆值得学习的部分，是完整的生命周期。** 可以按用途区分工作记忆、事件经验、抽象知识和程序性经验，但第一版不需要为每种记忆建一个独立服务。

| 记忆用途 | 示例 | 主要错误 |
| --- | --- | --- |
| 当前工作状态 | 正在谈判的交易与待办 | 压缩后丢失未决状态 |
| 事件经验 | B 在第 12 回合未履约 | 时间、对象或来源记错 |
| 抽象判断 | B 在粮食不足时违约风险高 | 从单次事件过度推广 |
| 程序经验 | 成交前重新读取余额与盟约状态 | 规则更新后仍沿用旧程序 |
| 用户偏好 | 更重视生存而非扩张 | 偏好变化后仍反复引用旧版本 |

我建议把流程理解为：观察 → 候选记忆 → 核验与来源 → 写入 → 检索 → 作为证据使用 → 更新或失效 → 必要时删除。每一步都可以独立失败。向量库只覆盖其中一部分。

个人版本可以从普通数据库或 JSON 记录起步，保留 owner、来源事件、发生时间、有效时间、类型、状态与被替代关系。时间条件和 Agent 可见性要在语义排序前筛选。这里的字段是本文建议，不是通用记忆标准。

**现有记忆系统的进展，适合按机制比较。** MemGPT 是分层虚拟上下文的早期基线；后续系统在时序、自动组织、检索融合与版本化上走了不同路线。下表不是产品排名，部分对象是研究方法，部分是当前工程实现。

| 系统或研究 | 值得学习的机制 | 对个人项目的启发 | 限制与核对点 |
| --- | --- | --- | --- |
| Zep / Graphiti | 区分事实生效时间与系统获知时间，保留关系的历史区间 | 用条约、传闻和追溯纠正测试时间语义 | 新输入不必然可信，矛盾识别也可能出错 |
| Mem0 | 抽取可复用信息，再按多种信号检索 | 分开比较建忆与读取的效果和成本 | 论文算法、Platform 与 OSS 不能混为同一实现 |
| A-MEM | 为笔记生成描述、标签和链接，更新相关笔记 | 消融“链接”和“经验演化”是否有收益 | 组织质量依赖模型，推断错误可能被强化 |
| Letta MemFS | Git 支持的文件记忆、按需读取、独立 Agent 仓库与显式共享 | 用 diff 检查记忆为何改变，尝试回滚错误经验 | 文件版本化不保证内容真实，也不等同业务事务 |

Zep 的论文重点是时间感知知识图，而非简单把文本切块后向量检索；它提供了适合学习“现实何时改变”和“系统何时得知改变”的案例。[Zep，2025-01](https://arxiv.org/abs/2501.13956)

Mem0 的 2025 年论文描述 ADD、UPDATE、DELETE、NOOP 决策；截至调研日的官方概念文档则把自动抽取描述为追加式，并要求应用显式 update/delete 来纠正或移除记忆。这是“读论文之后还要读当前接口语义”的具体例子。论文中的相对提升与 token 节省也不能直接视为你项目的收益。[Mem0 论文](https://arxiv.org/abs/2504.19413)、[当前 How it works](https://docs.mem0.ai/core-concepts/how-it-works)

A-MEM 的可学习之处是笔记结构与关联如何形成，并允许相关旧笔记演化。实验时保留原始事件，单独存放模型生成的解释；这样才能发现错误关联是否通过重复检索变得更难纠正。[A-MEM，2025 年研究](https://arxiv.org/abs/2502.12110)

Letta 当前 MemFS 把各 Agent 的文件记忆放在 Git 仓库，通过索引与按需读取控制活动上下文；它默认不自带向量索引。旧版 memory blocks 的更新语义不要直接套到 MemFS。其版本记录适合研究经验变更、共享范围与回滚。[Letta：MemFS](https://docs.letta.com/concepts/memfs)

**2026 年记忆评测有三个尤其值得读的进展。**

MemoryArena 把记忆与行动放进跨会话闭环：前期任务的经验影响后续相关任务。它直接提醒我们，回忆题上的高分不能保证后续行动成功。论文在 2026 年 9 月更新，适合为你的城邦实验设计跨回合依赖。[MemoryArena](https://arxiv.org/abs/2602.16313)

LongMemEval-V2 在 2026 年 5 月提出环境经验评测，覆盖状态、流程、常见陷阱和前提意识，并比较检索与文件工作区取证。其主要评估是从历史轨迹收集证据后回答问题，不能直接解释为在线工作流的完成率。[LongMemEval-V2](https://arxiv.org/abs/2605.12493)

Memora 在 2026 年 4 月提出遗忘感知指标 FAMA，处罚使用已经失效的记忆。它让“该忘掉或更正的东西是否仍在影响回答”成为显式测量对象，适合做盟约变化、情报纠正、偏好更新实验。[From Recall to Forgetting](https://arxiv.org/abs/2604.20006)

对你的游戏而言，记忆可以保留观察历史和外交判断，但权威状态仍在引擎中；对编码 Agent，记忆可以保留常见失败经验和工作方法，但当前 API、仓库结构和任务要求应重新核验。每次回忆前都问一句：这条信息现在仍有效吗？

**记忆污染的研究也从“有没有存进去”扩展到“造成什么后果、能否修复”。** 2026 年 7 月的 MemSecBench 使用 Write–Execute–Forget 流程，分别追踪内容持久化、后续行动与选择性修复。其攻击比例是特定配置和任务集的结果，适合借鉴评测结构，不宜当作所有记忆系统的风险比例。[MemSecBench](https://arxiv.org/abs/2607.27080)

城邦实验可以用合成谣言测试这个问题：传闻是否被升级成已确认事实？撤销传闻后，相关推断和经验是否仍在影响行动？来源证明信息来自哪里，不证明内容真实。要同时测错误记忆的影响和正常信息的可用性；若简单拒绝所有外部消息，可能减少错误，也破坏正常外交。另给各城邦不同的私有底线，交错查询和更新，验证服务端可见性过滤；仅靠提示词提醒保密不能作为访问控制实现。

**Harness 的学习价值在于把不确定的模型行为接到有明确语义的系统上。** 一个用于探索的最小 harness 可以包含：上下文构造、模型调用、动作解析、业务校验、执行、结果记录、结束条件，以及错误分类。模型输出的是候选行动，成功要由环境结果确认。

Anthropic 2026 年 3 月的长任务工程文章展示了生成与评估分离、结构化交接和逐项简化 harness 的案例。它还展示：模型升级后，部分此前有用的任务分解与检查步骤可以移除。这些是工程观察，文章中的案例并不是等预算、覆盖广泛任务的严格对照实验。[Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)

建议把 harness 中的措施分成两组：一组是针对模型能力不足的补偿，例如额外规划、分解和反思；另一组是系统语义，例如权限、持久化、幂等和验收。前者要随着模型和任务重新评估，后者不能仅因模型变强而省略。

一个最有后端学习价值的故障是：工具已经完成转账，但 Agent 在记录响应前崩溃。恢复后若再次转账，会重复产生副作用。仅保存聊天记录或 checkpoint 不足以解决。个人实验应比较固定操作 ID、工具端去重、结果查询和不确定状态保留，而不是让模型根据一句摘要猜测是否该重试。

LangGraph 当前 Functional API 文档说明：恢复可能重放入口逻辑，已保存的 task 结果可以复用，但启动后未完成的 task 可能再次执行。这正是学习 checkpoint 与外部副作用边界的入口。持久化不能单独保证外部服务的 exactly-once。[LangGraph：Functional API](https://docs.langchain.com/oss/python/langgraph/functional-api)

托管运行系统也开始把会话与计算环境分开管理。Anthropic 2026 年 4 月的工程设计将日志、harness 和 sandbox 解耦。选择托管或自建时，还应核对状态、文件、预算、取消与恢复各自的生命周期；日志与文件未必具有相同的保留期限。[Claude Managed Agents 工程设计](https://www.anthropic.com/engineering/managed-agents)

**RLM 是一个值得进阶探索的具体方向。** Recursive Language Models 将大输入留在外部环境，模型通过程序检查、拆分，并对片段发起子调用。它把“读取所有内容”转成“决定怎样处理内容”。2026 年 5 月修订版同时报告了长尾调用成本、顺序子调用的延迟和安全边界等限制。[RLM 原论文](https://arxiv.org/html/2512.24601v3)、[作者实现](https://github.com/alexzhang13/rlm)

适合你的任务不是单个事实检索，而是需要覆盖许多记录的分析，例如“哪个城邦在每次粮食危机之前都提高了价格？”或“找出跨服务发生的重试链”。比较普通检索、固定分块汇总、可查询文件工作区和受限 RLM。语义判断与精确聚合应有各自的验证依据。

2026 年 7 月作者进一步研究 harness 如何通过程序分解帮助跨长度和跨领域泛化；2026 年 8 月又探索在代码流式生成时提前启动可安全推测的子调用。这些方向很有启发，但仍需要按任务验证，尤其不能提前执行不可撤销的写操作。[组合泛化研究](https://alexzhang13.github.io/blog/2026/harness/)、[Speculative Programmatic Tool Calling](https://alexzhang13.github.io/blog/2026/spec-ptc/)

对个人项目，先限制递归深度、子调用数量、总 token 和墙钟时间；记录高成本失败轨迹。不要从“论文在某些任务上更高效”推导成“RLM 总是更便宜”。

**经验优化是下一阶段值得学的方向，先区分改变上下文与改变权重。**

ACE 把经验组织成可增量更新的上下文条目，强调反思与整理，避免不断重写一个越来越笼统的提示。2026 年 3 月修订版也研究有害经验导致的退化。其在线适应协议不能直接当作冻结模型后的未见任务泛化成绩。[ACE v3](https://arxiv.org/html/2510.04618v3)

GEPA 从运行轨迹、错误和反馈中提出提示修改，再用评估选择候选。2026 年 7 月作者实现加入并行候选提案，展示了优化耗时与候选搜索的改进。它适合实验工具说明与技能优化，但比较成本时还要计算提出和反思候选的模型费用。[GEPA 论文](https://arxiv.org/abs/2507.19457)、[并行 proposal 更新](https://gepa-ai.github.io/gepa/blog/2026/07/30/parallel-proposals/)

Fast-Slow Training 的 2026 年 5 月研究进一步结合上下文优化与 RL 参数更新。可以学习其“经验先在上下文适应，再影响参数”的思想；对于业余起步，先做不改变权重的经验实验，更容易明确成本、回滚和错误来源。[FST](https://arxiv.org/abs/2605.12484)

这种研究的难点是验证迁移：经验可能只是答案缓存，语言反馈可能错误，修复一个任务可能伤害另一个任务。改进流程需要开发集、独立留出集和历史回归，而不是让同一个模型评价自己刚写出的经验。

**多 Agent 的研究开始更认真地比较任务结构和总预算。**《Towards a Science of Scaling Agent Systems》2026 年 4 月版本比较了 260 种配置与六类基准；它发现可并行任务和顺序任务的收益不同，并在部分编码任务上观察到多 Agent 的退化。它提供选型线索，不能当作所有模型和业务的通用公式。[论文 v3](https://arxiv.org/html/2512.08296v3)

在你的游戏里，多个城邦是模拟对象，不意味着每个城邦内部还需要 planner、executor、critic 三个 Agent。先让一个策略组件完成每个城邦的决策，再比较两个独立情报调查者是否改善决策；同时计入通信与汇总成本。

**评估也开始覆盖“正确知识是否真的变成正确操作”。** τ-Knowledge / τ³ 把文档、政策、用户交互和后端动作放在一起。首发实验中，即使提供正确文档，最佳任务成功率仍不到四成；这是特定模型与任务的结果，但说明检索成功不能替代执行验证。2026 年 7 月判分修订影响 banking_knowledge 域，该域旧版分数不能与当前成绩直接横比；其他域不受该修订影响。[τ-Knowledge 原论文](https://arxiv.org/html/2603.04370v1)、[官方版本说明](https://github.com/sierra-research/tau2-bench/blob/main/README.md)

另一个关键区分是 pass@k 与 pass^k：前者关注 k 次尝试至少成功一次，后者关注 k 次全部成功。在同题每次独立、成功率都是 75% 的简化条件下，三次至少一次成功约 98.4%，三次全成功约 42.2%。真实评估要逐题聚合，检查独立性；这个例子是数学说明，不是某个模型的测量结果。[Anthropic：Agent evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

**个人探索可以从下面五个实验中挑一个开始。** 时间是按熟悉基本模型调用、已有可运行环境估计；实际接入与调试可能更久。实验都是建议方案，本次调研未运行。

| 实验 | 核心问题 | 最小版本 | 大致投入 |
| --- | --- | --- | --- |
| A：压缩保真实验 | 压缩到底丢了什么？ | 合成日志、标注规则、三种压缩方法 | 2～4 个晚上 |
| B：记忆纠错实验 | 旧经验何时应失效？ | 带时间与纠正事件的短历史 | 3～5 个晚上 |
| C：中断恢复实验 | 续接任务会不会重复执行？ | 模拟工具与可注入的崩溃点 | 约一周 |
| D：外部上下文实验 | 查询工作区何时胜过全文输入？ | 日志文件与标准答案 | 约一周 |
| E：经验改进实验 | 学到的是可迁移经验还是题目答案？ | 失败记录、候选技能、留出场景 | 1～2 周 |

**实验 A：比较压缩后信息保留与真实行为。** 准备 10 条开发场景、20 条留出场景，日志里包含一般闲聊、任务约束、金额、否定条件、操作 ID、未确认的结果和后续纠正。对照最近 N 条截断、普通自由文本摘要、结构化摘要加受保护字段；在容纳得下的样本上增加完整上下文对照。首先用人工标注的字段评估，再让 Agent 执行下一步。

看五项结果：约束召回、数值与对象正确率、不确定状态保留、违规或重复动作率、总成本。普通摘要可能足够好；结构化字段也可能遗漏未预见的信息。这种负结果同样有用。

**实验 B：测试记忆的修订、冲突和时效。** 设计 B 违约、后来证实是港口封锁、随后恢复履约、盟约又到期的时间线。比较无跨会话记忆、原始事件检索、抽取事实、带有效时间和替代关系的记忆。开发集与留出集更换名字、时间、事件顺序和纠正方式，避免只匹配模板。

分别测“正确取出证据”和“用证据正确行动”。包括当前事实准确率、过期信息引用率、来源覆盖、跨 Agent 可见性违规、任务完成情况。解释性语言只作辅助分析，不作为唯一判分依据。

**实验 C：在工具调用周围制造故障。** 准备一个模拟资源转移工具，在提交前、执行成功后、响应持久化前等位置中断进程。比较仅恢复聊天历史、checkpoint 恢复、checkpoint 加稳定操作 ID 和结果查询。对每个位置检查最终余额和操作记录，并区分明确失败、明确成功、结果未知。

主要指标是重复副作用次数、丢失操作次数、恢复后的终态正确性和恢复耗时。这个实验可以大量使用脚本策略与录制输出，减少模型费用；它检验的是系统恢复语义，没必要让每轮故障都调用模型。

**实验 D：给历史事件做“检索题”和“全局分析题”。** 一类问题只需要一两条记录；另一类要求统计、比较或覆盖许多事件。比较全文输入、关键词/向量检索、固定分块、受限的可编程工作区。所有组使用相同数据与答案标准，给出相同资源上限，并分别记录实际使用量。

指标包括答案正确性、覆盖率、证据来源、总调用数、运行时间和尾部成本。先让代码处理有明确规则的过滤与聚合，再观察模型的语义判断何时有额外价值。

**实验 E：让一次失败产生可审查、可撤回的经验。** 从开发集失败轨迹提取候选经验，写成短程序或技能说明；在留出场景验证后才使用。比较固定提示、只存成功案例、从成功与失败中生成经验、经过验证的经验。经验改变后还要跑原场景，检查是否产生回归。

例如“资源不足时先确认成交是否已发生，再决定是否重试”可以迁移；“第 17 题要选交易对象 C”则是泄漏答案。世界规则改变后，经验应允许过期或回滚。

**评估方法应当比项目界面更早建立。** 对城邦环境优先写可执行的终态断言：粮食不为负、交易仅结算一次、没有使用不可见情报、目标是否完成。对代码任务使用独立测试和运行结果。语言裁判适合解释质量等难以完全规则化的方面，但要抽样与人工判断核对。

比较时固定模型及设置、工具接口、任务集、信息可见性和预算，先只改一个因素。环境随机种子可以固定，模型输出仍可能有变动；不要把温度为零当作完全确定性的保证。录制模型动作可以帮助重放引擎，但重新请求模型属于新实验。

总成本应包括摘要、记忆提取、检索、embedding、反思和验证，不能只算最后回答。既记录成功率，也记录平均成本、每次成功的成本、调用数和长尾轨迹。小样本不要过度解释显著性或尾部百分位；先把每条任务的原始结果保留下来。

开发集用于修改系统，留出集用于检验迁移，失败集用于回归。初期可以用 10 个开发场景、20 个留出场景，每组重复 2～3 次作为探索；这个规模不代表能够得出全领域结论。

**一条比较容易坚持的路线，是前四周做基础，后四周任选进阶。**

| 周次 | 重点 | 必须留下的结果 |
| --- | --- | --- |
| 第 1 周 | 最小循环、工具校验、运行记录、规则策略 | 能逐步解释一次执行为什么成功或失败 |
| 第 2 周 | 实验 A：截断与压缩 | 三种策略的逐场景结果与失败分类 |
| 第 3 周 | 实验 B：记忆更新与时效 | 旧信息引用率、正确证据与动作的比较 |
| 第 4 周 | 实验 C：恢复与幂等 | 故障点与终态正确性表 |
| 第 5～6 周 | 选 RLM、工作区检索或经验优化之一 | 有预算上限的对照与负结果 |
| 第 7～8 周 | 验证跨场景迁移，删除无效组件 | 能说明每个保留组件解决哪个失败 |

主项目可以继续用你熟悉的后端语言；论文复现用独立的小脚本即可，不必把整个项目迁移。第一阶段用普通数据库或文件存储、少量工具和一个 Agent，足以理解多数关键问题。是否加入向量库、图数据库或多 Agent，应由实际检索、时序或任务分解需求决定。

你前面提到的认知所有权，可以作为一个额外观察：每次让 AI 加入一项机制之前，自己写下它预计修复的失败、它改变的状态边界、验证方式和失败后的恢复行为。实验结束时先预测哪一组会更好，再看结果。学习成果会是一组经过检验的判断，而不仅是一个不断变大的项目。
